# R5-M10 — E2E

## 1. Objetivo

Cubrir con pruebas end-to-end (navegador → API → DB → UI) el flujo completo de aprobación: creación de Change Request, ruteo, decisión (aprobar/rechazar), aplicación, y reflejo del resultado tanto para el solicitante como el aprobador.

## 2. Problema que resuelve

Los tests unitarios/integración de M00-M09 verifican piezas aisladas; R5-M10 verifica el flujo real tal como lo experimenta un usuario.

## 3. Estado actual del repositorio

MISSING — depende de todo R5-M00..M09 y de R4 (Employee Portal) para la creación del Change Request desde el lado del empleado.

## 4. Alcance IN

- Escenario feliz: empleado solicita cambio → política AREA_RESPONSIBLE → responsable aprueba → nueva versión draft creada → solicitante ve el cambio reflejado.
- Escenario de rechazo: aprobador rechaza con motivo → solicitante ve el motivo.
- Escenario NO_APPROVAL: cambio se aplica automáticamente sin bandeja.
- Escenario de conflicto de concurrencia (dos aprobadores intentan decidir a la vez).

## 5. Alcance OUT

- Pruebas de carga/performance (fuera de alcance de un piloto MVP).

## 6. Dependencias

R5-M00..M09, R4-M12 (Employee E2E, reutiliza fixtures de creación de Change Request).

## 7. Decisiones arquitectónicas

Se reutiliza el framework de E2E ya en uso (`qa/e2e-acceptance/`, Playwright-style, visto en el baseline para ingestión) en lugar de introducir una herramienta nueva.

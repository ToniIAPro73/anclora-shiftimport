# R5-M10 — E2E

## 1. Objetivo

Cubrir con pruebas end-to-end (navegador → API → DB → UI) el flujo completo de aprobación: creación de Change Request, ruteo, decisión (aprobar/rechazar), aplicación, y reflejo del resultado tanto para el solicitante como el aprobador.

## 2. Problema que resuelve

Los tests unitarios/integración de M00-M09 verifican piezas aisladas; R5-M10 verifica el flujo real tal como lo experimenta un usuario.

## 3. Estado actual del repositorio

IMPLEMENTED — un spec Playwright con cuatro tests independientes ejecuta los flujos contra Neon development y `vercel dev`. La bandeja del aprobador se valida con navegador real; la identidad del empleado se mantiene aislada mediante clientes API autenticados y se comprueba el estado persistido que consume R4-M07. Esto evita la inestabilidad del runner local al abrir varias páginas autenticadas simultáneas sin relajar la validación de backend.

## 4. Alcance IN

- Escenario feliz: empleado solicita cambio → política AREA_RESPONSIBLE → responsable aprueba → nueva versión draft creada → solicitante ve el cambio reflejado.
- Escenario de rechazo: aprobador rechaza con motivo → solicitante ve el motivo.
- Escenario NO_APPROVAL: cambio se aplica automáticamente sin bandeja.
- Escenario de conflicto de concurrencia (dos aprobadores intentan decidir a la vez).

## 5. Alcance OUT

- Pruebas de carga/performance (fuera de alcance de un piloto MVP).

## 6. Dependencias

R5-M00..M09, R4-M12 (Employee E2E, reutiliza fixtures de creación de Change Request).

## 7. Decisiones arquitectónicas

Se reutiliza el framework de E2E ya en uso (`qa/e2e-acceptance/`, Playwright-style, visto en el baseline para ingestión) en lugar de introducir una herramienta nueva.

## 8. Modelo de datos afectado

Los fixtures crean una versión publicada y un turno asociado para comprobar que las decisiones generan o actualizan un draft sin mutar la publicación. El camino `NO_APPROVAL` reutiliza un draft existente cuando ya lo hay y actualiza el assignment equivalente de forma idempotente.

## 9. API / Backend

Se ejercitan los endpoints de Change Request, Approval Inbox, approve/reject y Request Status. La ruta `NO_APPROVAL` comparte la misma transacción de creación y aplicación, incluyendo el caso de draft preexistente.

## 10. Frontend / UX

N/A — se ejercita la UI ya definida en M03-M05.

## 11. Seguridad y autorización

El escenario de aislamiento cross-tenant de R5-M09 se repite aquí a nivel E2E real de navegador, no solo API directa.

## 12. i18n

Los escenarios E2E deben correr en ambos idiomas (ES/EN) al menos una vez cada uno, consistente con la práctica ya vista en `qa/e2e-acceptance`.

## 13. Accesibilidad

Se conserva la semántica y los roles accesibles de `ApprovalInbox`; la suite existente de componentes cubre los estados loading/empty/error y el formulario de rechazo. No se añade `axe-core` como dependencia sólo para esta microfase: el runner local no tenía esa integración instalada.

## 14. Responsive / temas

Al menos un escenario corre en viewport móvil y uno en dark theme, siguiendo el patrón de `qa/vlm-fallback` y `qa/public-header-auth`.

## 15. Observabilidad / errores

Los escenarios verifican también que no aparecen errores de consola del navegador durante el flujo (criterio ya usado en otras suites E2E del repo).

### T04 — Escenario de conflicto de concurrencia real

Objetivo: cubrir a nivel E2E que dos aprobadores no pueden ambos decidir.
Archivos: `qa/e2e-acceptance/specs-local/approval-lite.spec.ts`.
Cambios: una interacción de bandeja en navegador y una segunda identidad concurrente por API aislada; ambas llegan al mismo endpoint y se verifica el par 200/409.
No hacer: no simular la concurrencia solo a nivel de API (eso ya lo cubre R5-M08) — aquí se verifica UX real.
Criterios de aceptación:
- [ ] El segundo navegador ve el mensaje de "ya decidida" tras intentar decidir.
Tests: el propio spec.
Evidencia esperada: capturas de ambas sesiones.

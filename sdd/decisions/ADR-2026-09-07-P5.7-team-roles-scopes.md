# ADR-2026-09-07 — P5.7 Team, Roles, Scopes & Organizational Management

## Metadata
- **Status**: APPROVED / CONTRACTUAL
- **Date**: 2026-09-07
- **Scope**: Anclora ShiftImport P5.7 Core Domain Architecture
- **Supersedes / Refines**: PD-2026-09-06-D05 (Planner scope without area)

---

## Context & Problem Statement
ShiftImport expanded from a standalone shift importer to an operational shift planning platform featuring organizations, users, memberships, employees, areas, schedule versions, and change requests.
However, the user experience and conceptual model became fragmented:
1. Technical entity boundaries (`users`, `memberships`, `employees`) leaked into the interface.
2. Managers who are also employees suffered conceptual conflation between administrative duties and personal shift requests.
3. Planners were constrained to a single area, preventing multi-area planners or employee-based rosters in organizations without areas.
4. Operational assignments (employee to area, planner to area) lacked temporal validity (`valid_from` / `valid_to`), causing historical context to be overwritten upon transfers.
5. The sidebar was cluttered with redundant options ("Usuarios" vs "Áreas" vs "Equipo") and mislabeled ("Aprobaciones" instead of "Solicitudes").

---

## Contractual Decisions (D1 – D12)

### D1. User != Employee
- **Decision**: `USER` and `EMPLOYEE` remain separate domain entities in DB and API.
  - `USER`: Account capable of authenticating (email, credentials, session).
  - `EMPLOYEE`: Operational identity capable of receiving shifts and appearing on rotas.
- **Cardinals**:
  - User without Employee (e.g. non-operational Owner/Admin)
  - Employee without User (e.g. staff without login access)
  - User + Employee (operational staff with login)
- **UI Principle**: The UI presents a unified "Persona" management experience without conflating database tables.

### D2. Employee Relation Does Not Reduce Role Authority
- **Decision**: An associated `Employee` record does NOT degrade the user's role authority.
  - `OWNER` + Employee maintains full `OWNER` authority.
  - `ADMIN` + Employee maintains full `ADMIN` authority.
  - `PLANNER` + Employee maintains full `PLANNER` authority.
  - `EMPLOYEE` user has `SELF` scope.

### D3. Areas Are Optional
- **Decision**: An organization may operate with 0, 1, or N areas. The system MUST NEVER force the creation of areas. Empty state for 0 areas is informative, not an error state.

### D4. Planners Are Optional
- **Decision**: Organizations can operate fully with `OWNER`, `ADMIN`, and `EMPLOYEES` without any `PLANNER`. An `ADMIN` can execute planning if permitted.

### D5. Planner Scopes: Organization, Areas, Employees
- **Decision**: A `PLANNER` can manage shifts and schedules under three distinct scope modes:
  1. `ORGANIZATION`: Unrestricted organization-wide planning.
  2. `AREAS`: One or more assigned active areas.
  3. `EMPLOYEES`: An explicit set of assigned employees (vital for roster-based planning without areas).
- **Rule**: If an org has no active areas, an unassigned Planner operates with `ORGANIZATION` scope. If an org has active areas and no assignment is made, Planner scope is `SCOPE_UNAVAILABLE`.

### D6. Role + Scope + Action + Target Canonical Authorization
- **Decision**: Authorization is formalized via `can(actor, action, target)`. No ad-hoc, dispersed authorization logic across components or endpoints.

### D7. Ownership Transfer Special Operation
- **Decision**: Changing the organization `OWNER` is NOT a regular role edit dropdown.
  - Must be an explicit, dedicated transactional operation: `TRANSFER_OWNERSHIP`.
  - Only the current active `OWNER` can initiate it.
  - The organization must maintain exactly 1 `OWNER` invariant at all times.

### D8. Effective-Dated Operational Assignments
- **Decision**: Operational assignments (Employee to Area, Planner to Areas, Planner to Employees) support temporal validity: `valid_from` and `valid_to` (nullable for open-ended).
  - Preserves historical continuity (e.g. Jan-Jun Area A, Jul-Dec Area B).
  - Overwriting historical assignments is prohibited.

### D9. Employee Requests vs Manager Direct Actions
- **Decision**: A manager acting as an employee (submitting a shift request) participates in the standard request workflow. A manager direct action (e.g. manual calendar edit by Admin/Owner) is an administrative edit, distinct from an employee request.

### D10. Requests Visible Label Replaces Approvals
- **Decision**: The visible navigation and workspace label is "Solicitudes" ("Requests") / "Solicitudes pendientes" ("Pending Requests"), NOT "Aprobaciones". A request can be either approved or rejected. Internal backend endpoints may retain `/approval-requests` for compatibility.

### D11. Anti-Self-Approval Contract
- **Decision**: If a user with `OWNER`, `ADMIN`, or `PLANNER` role submits a request regarding their own shift using the employee request flow, they CANNOT approve or reject their own request. Self-approval is strictly forbidden and rejected server-side.

### D12. Operational UI Displays Active Areas & Current Assignments
- **Decision**: Operational dropdowns, selectors, and calendar filters only display ACTIVE areas and CURRENT (active for current operational date) assignments. Historical assignment reporting is explicitly DEFERRED.
